## D-001 失物（lost）的状态机

**决定**：`items.status` 对两种类型共用一列，但取值分两套：

| 类型 | 允许的状态 | 含义 |
|---|---|---|
| `lost` | `open` → `reunited` → `archived` | 未找到 / 已找回 / 归档 |
| `found` | `pending_storage` → `stored` → `claim_pending` → `ready_for_pickup` → `returned` → `archived` | 计划书表 5 原样 |

**理由**：计划书的 6 态只对招领成立，"待存放/已存放"对失物无意义。
**影响**：前端状态徽章按 `type + status` 双维度映射；后端状态迁移校验按类型分派。
**状态**：已确认（小冯 agree，2026-11-18）

## D-002 地点匹配不建词典

**决定**：地点维度只用「全文相同 / 互相包含 / 关键词重合」判分，不引入地点词典或地理编码。
`reasons` 里如实写「地点相近」，不声称"同区域"。

**理由**：计划书要求"同区域得 12 分"但没给区域定义；建词典需要学校真实地点清单（OI-05 未确认）。
**影响**：匹配分可能偏低 → 阈值 45/70 需在上线后用真实数据回调，`matches` 表已存 `score` 便于调参。
**状态**：已确认

## D-003 时间缺失时的计分

**决定**：`event_at` 任一方为空 → 「时间接近」项记 0 分，`reasons` 追加「时间未知，未计分」。

**理由**：计划书规定事件时间可选；按 0 分处理可避免用"当前时间"顶替造成假高分。
**影响**：匹配总分上限在缺时间时为 80。前端展示 reasons 时需容错这条。
**状态**：已确认

## D-004 匹配通知去重

**决定**：`matches` 以 `(lost_item_id, found_item_id)` 唯一。分数首次达到 70 时发一次站内消息，
之后同一对再重算（编辑、确认存放）只更新 `score` 与 `reasons`，**不重复发消息**。
若分数曾掉到 70 以下再升回 70 以上，仍不重发（以"已通知过"为准，记在 `matches.notified_at`）。

**理由**：计划书要求"每次编辑都重算"，若不去重会刷爆消息中心。
**影响**：`matches` 增加 `notified_at` 字段（计划书表 9 之外，属实现细化）。
**状态**：已确认

## D-005 认领的"提议"与"确认"

**决定**：计划书 §4.5 与 §3 权限矩阵对"发布者能否最终确认"表述冲突，按双签实现：

1. 申请人提交 → `claims.status = pending`，物品 `status = claim_pending`
2. **发布者**可以 `agree`（提议）或 `reject`（拒绝），记录在 `claims.publisher_verdict`
3. **授权角色**（所属存放点志愿者 / 管理员；保卫处暂定）做最终 `approve` / `reject`，记 `claims.reviewed_by`
4. 最终通过要求：`publisher_verdict != reject` 且授权角色 `approve`；否则流程不通
5. 一条物品通过后，其余 pending 自动 `rejected`，`review_note` 写明「物品已归他人」

**理由**：既尊重"发布者参与确认"，又保证"授权角色最终确认"，且不改变计划书的接口清单。
**影响**：`claims` 增加 `publisher_verdict`、`publisher_verdict_at`；前端详情页要显示两段状态。
**状态**：已确认

## D-007 矛盾 5 分钟上报规则

**决定**：两边出现**真分歧**（各持一套方案、互不让步）且 **5 分钟内**无法在 issue 里收敛 → 立即上报人类（`to:human` 标签 + 对话里直说），不再等 24 小时。

- 「没看到消息」不属于分歧，走 L1（24h 沉默自动推进）
- 不可逆操作、影响 11-23 节点、权限安全、文档冲突 → 立即上报，不受 5 分钟限制
- L2 期间只停被卡的那条分支，另一方继续干不受影响的部分

**理由**：人类 2026-11-18 指令——不希望两个 AI 在错误方向上互相说服。
**影响**：`docs/分工协议.md` §5 与 `AGENTS.md` §9 已同步改写。
**状态**：已确认（人类指令）

## D-009 界面类分歧不上报人类

**决定**：界面设计、版式、配色细节、文案、代码风格、目录命名等分歧，**由两个 AI 在 issue 内自行谈定**，
不上报人类；谈不拢按 L1 沉默规则由提议方先做。

**升级条件**（仅这三种）：需要花钱、需要学校素材（校徽/官方名称/真实照片）、会让 11-23 交不出来。

**理由**：人类 2026-11-18 指令——「界面设计等你们自己以后聊即可」，不想被这类细节占用注意力。
**影响**：`docs/分工协议.md` §5 已加"明确不上报"清单；`to:human` 标签不用于界面分歧。
**状态**：已确认（人类指令）

## D-010 交接必须等对方确认，不得替做

**决定**：凡是要另一个 AI 做的事，一律等对方"看到 + 回复 + 做完"；在他确认前，**不推进依赖他的工作，也不替他做**。

**优先于 L1**：交接类任务不适用"48 小时自动推进"。L1 只适用于非交接的自有任务（如自己选库、自己定实现）。

**理由**：人类 2026-11-18 指令——「遇到需要另一个 AI 做的事情就等会，等到另一个 AI 看到消息并回复做好了再做」。
替做会破坏目录所有权，也掩盖真实的进度。

**影响**：
- 小冯的 DRAFT PR 不转 Ready 就不合
- 他答应但未交付的，必须先要一句"已完成"
- 卡住的交接要上报人类，而不是自行绕过

**状态**：已确认（人类指令）

## D-011 提问 5 分钟无回应必须提醒

**决定**：向对方提出需要回答/决策/动手的问题后，**5 分钟内没有回应就主动提醒**，不许默默等。

提醒分两步：① 在 issue 里追加一条提醒；② 在给人类的回复里明说「他没回，需要你去那台机器上说一句」。

**适用范围**：提问、承诺未交付 → 提醒；纯通知、对方已给出明确时间点 → 不提醒。

**理由**：人类 2026-11-19 指令。更根本的原因是——**对方的 AI 不会自己醒**，
只有他那边的人说话它才会动。所以"再等一会儿"没有意义，必须把球交回人类手里。

**影响**：`docs/分工协议.md` §5 已加"提问 5 分钟无回应 → 提醒"小节；
实现方式是提问后启动 5 分钟观察窗口，超时即触发两步提醒。
**状态**：已确认（人类指令）

## D-012 广场对游客只读开放（覆盖需求基线 §3）

**决定**（人类 2026-11-19 拍板）：**游客无需登录即可浏览广场与物品详情**，写操作全部仍要登录。

| 接口 | 变更 |
|---|---|
| `GET /api/items` | 匿名可读，`viewer = null` |
| `GET /api/items/:id` | 匿名可读 |
| `POST /api/items`、`PATCH`、`/claims`、`/favorite`、`POST /api/uploads` | **不变，仍要登录** |

**匿名字段口径**：`isOwner = false`、`isFavorited = false`、`contact = null`、
`author` 保留 `id + name + isVolunteer`（详情页要显示"谁捡到的"，这是认领的前提，且不含联系方式）。

**匿名限流**：按 IP **60 次/分钟**，超限 429。理由：读接口开放后可能被脚本爬取。

**覆盖的需求基线条文**：
- §3「物品信息需要登录后查看」
- §2.2「游客只能看到登录和注册页面」

**理由**：失物招领的价值在传播——捡到东西的人往往还没注册，要求先登录会直接丢掉这批人。

**影响**：
- `src/api/index.js` 去掉两处 `requireUser`，改为匿名限流
- 前端未登录时的引导卡片、`isFavorited` 恒 false 的展示
- `docs/API契约.md` §2 权限说明已同步
**状态**：已确认（人类拍板）
