# 分工协议（小灰 × 小冯）

> 生效日期：2026-11-18　　版本 v1
> 变更方式：改本文件必须开 PR，且人类知情

---

## 1. 角色与边界

| | **小灰**（`xiaohui`） | **小冯**（`agent-b`） |
|---|---|---|
| 定位 | 主控 / 后端 / 合并者 | 协作 / 前端 / 测试 |
| 拥有目录 | `src/**`、`scripts/**`、`.github/**`、根配置 | `public/**`、`tests/e2e/**` |
| 共有 | `docs/**`（各写各的前缀）、`journal/**`（各写自己段落） | 同左 |
| 合并权 | **有**（squash merge） | 无（只能开 PR） |
| 提交尾注 | `Agent: 小灰` | `Agent: agent-b` |
| 分支前缀 | `xiaohui/` | `b/` |

**硬边界**：谁都不许改对方的目录。需要改 → 开 issue 说明，由对方改。

---

## 2. 阶段划分与依赖

```
M1 数据与认证（小灰）  ──┐
                          ├─→ M3 联调（双方）
M2 前端外壳（小冯）    ──┘
                          ↓
                    M4 匹配与认领（小灰） + 管理后台 UI（小冯）
                          ↓
                    M5 部署（小灰） + E2E（小冯）
```

| 阶段 | 小灰 | 小冯 | 依赖关系 | 目标 |
|---|---|---|---|---|
| **M1** | schema 11 表、迁移/种子、注册/验证码/登录/会话/CSRF | — | 无 | 浏览器能注册并登录 |
| **M2** | — | 七视图外壳、广场页、mock 数据、390/1280 响应式 | 只需 `docs/API契约.md` | 能点、能看、能切视图 |
| **M3** | 物品 CRUD + 图片 + 状态机 | 接真实接口、发布页、详情页 | 需 M1 完成 + 契约不变 | 发布→列表→详情感通 |
| **M4** | 匹配、认领、消息、后台接口 | 认领页、消息中心、后台 UI | 依赖 M3 | 认领全链路 |
| **M5** | 部署、备份、HTTPS | E2E 用例、移动端复查 | 依赖 M4 | 公网可访问 |

**关键规则**：M1 和 M2 **完全并行**，互不等待。小冯不需要等我的接口，我也不会为了前端改契约——契约一旦锁（`docs/API契约.md`），改动要开 issue 双方确认。

---

## 3. 唯一接口：契约文件

`docs/API契约.md` 是两端唯一的约定。规则：

- 字段名、状态码、错误体，**以文件为准**，不以任何一方口述为准
- 前端按契约写 mock，后端按契约实现
- 发现不一致：**不许自行修改**，开 `to:xiaohui` + `kind:question` 的 issue，由小灰裁定并更新契约（契约变更需 commit 记录）

---

## 4. 日常节奏

| 时间 | 人类说 | 双方做什么 |
|---|---|---|
| 12:00 | "同步" | 跑 `sync.ps1` → 处理 `to:我` 的 issue → 推进自己分支 |
| 21:00 | "同步" | 收尾：push 分支、开/更新 PR、写 `journal/当天.md` |

**PR 规则**：合并前必须 ① 自己跑过 ② 自查清单勾完 ③ 无冲突。小灰的 PR 由小冯看一眼 diff，反之亦然。

---

## 5. 矛盾怎么处理（三级）

| 级别 | 情形 | 处理 | 谁决定 |
|---|---|---|---|
| **L0 自动** | 已有答案：`docs/决策记录.md`、`docs/需求基线.md`、`docs/API契约.md` 里有明确规定 | 照做，不问 | 文档 |
| **L1 超时自动** | 一方提出方案，对方 24h 未回；48h 仍未回 | 按提议方方案先做，issue 写明"可回滚" | 提议方 |
| **L2 必须问人类** | ① 涉及**不可逆**操作（删数据、改表结构、force push）② 影响 **11-23 里程碑** ③ 权限/安全/隐私 ④ 两份文档互相冲突 ⑤ 双方各持方案、48h 无法收敛 | **立刻停这块**，开 issue 打 `to:human`，并在对话里直接问人类 | **人类** |

### L2 的提问格式（对人类）

人类只看到一句话 + 两个选项，不做技术判断：

> **要你拍板**：<一句话说清分歧>
> A. <方案A 的后果，一句话>
> B. <方案B 的后果，一句话>
> 我倾向 A，因为 <一句理由>。

裁决结果**必须**写进 `docs/决策记录.md`（新编号 D-00X），否则下次还会吵。

**停摆规则**：L2 期间，被卡的那条分支暂停，**另一方继续干不受影响的部分**——不允许两个 AI 一起停下来等人。

---

## 6. 交接规则

- 每个阶段结束，在自己分支的 PR 描述里写「完成 / 未完成 / 已知问题」
- 每天一篇 `journal/YYYY-MM-DD.md`，只追加自己的段落
- 跨阶段依赖（如 M3 需要 my API 就绪）：在 issue 里写「我这边 X 月 X 日可用」，不靠嘴说

---

## 7. 争议留痕

所有决定落到三处之一：

| 决定类型 | 记录位置 |
|---|---|
| 需求怎么理解 | `docs/决策记录.md`（D-00X） |
| 接口/字段 | `docs/API契约.md`（改要 commit） |
| 临时协调 | issue 评论 |

**口头说定的事一律无效**——两边的 AI 都会忘记，仓库不会。

---

## 8. 人类需要做什么（就这 4 件，其余全自动）

| # | 事项 | 频率 | 为什么必须由人做 |
|---|---|---|---|
| 1 | 说「同步」 | 每天 2 次 | 两个 AI 无法互相唤醒，只有人能触发 |
| 2 | 对 L2 矛盾拍板 | 预计每周 1-3 次 | 需要项目目标的判断，不是技术判断 |
| 3 | 提供 SMTP 授权码 | 一次性 | QQ/腾讯企业邮的授权码只能本人申请 |
| 4 | 决定公网部署方式 | 一次性 | 涉及备案、费用、学校是否许可 |

**不需要人做的事**（已全部自动化）：建仓库、开分支、提交推送、开 PR、合并、发留言、取留言、
写日志、跑测试、改 issue 标签、邀请协作者、加 SSH 密钥、配分支策略。

**可选项**（不做也能跑）：把仓库转为公开（只为开启 GitHub 分支保护的强制约束）。

---

## 9. 本协议的自动执行检查

每次同步跑 `scripts/sync.ps1` 时应当能看到：

- 是否有发给我的未读留言
- 我的 PR 是否有冲突
- 分支是否落后 main

缺任何一项，说明协作基建坏了，先修基建再写代码。
