## 演示当天的网络方案（按可达性从强到弱）

| 方案 | 老师能看到 | 成本/耗时 | 前提 |
|---|---|---|---|
| **A. 公网 HTTPS** | ✅ 任何网络 | ¥25-60/月，约 15 分钟（`deploy/install.sh`） | 有服务器 + 域名 |
| **B. Cloudflare 隧道** | ✅ 任何网络 | 免费，约 10 分钟（`scripts/tunnel-up.ps1`） | 本机常开 |
| **C. 同一 Wi-Fi 局域网** | ⚠️ 只有连同一网络的设备 | 0，1 分钟 | 无 |

### 方案 C 怎么做（0 成本兜底）

服务默认监听 `0.0.0.0`，局域网本来就可达（已验证：本机 `http://172.17.211.79:3000/health` 返回 200）。

```powershell
npm start                                    # 起服务
# 查本机 IP（看 WLAN 那行的 IPv4）
ipconfig | Select-String 'IPv4'

# 放行防火墙端口（管理员 PowerShell，只需一次）
New-NetFirewallRule -DisplayName "湘寻演示" -Direction Inbound -LocalPort 3000 -Protocol TCP -Action Allow
```

然后手机连**同一 Wi-Fi**，浏览器打开 `http://你的IP:3000`。

**局限**：老师如果不在同一网络就打不开；且是 HTTP 不是 HTTPS，验收项 A-01 不算通过。
**但它能证明"手机上真的能用"**——移动端适配、真实点击、真实数据，比只在本机屏幕上看有说服力。

**为什么分三层**：它们能发现不同的问题。

| 层次 | 工具 | 能发现 | 发现不了 |
|---|---|---|---|
| 接口层 | `demo-check.mjs` | 数据链路断、状态机错、匹配不触发 | 按钮在不在 |
| 界面层 | `tests/e2e`（7 场景） | 页面白屏、按钮点了没反应、权限门禁 | 整条演示流程的连贯性 |

## 主线一：捡到东西的人（90 秒）

**讲什么**：为什么捡到东西的人愿意用——不用注册就能看，发布只要 30 秒。

1. **先演示游客**（用隐身窗口，不登录）
   - 打开首页 → 广场能看到 4 条信息
   - 搜索框输「耳机」→ 立刻筛出那条
   - 点进详情 → 能看到分类、地点、时间、描述、存放点

   > **话术**：「捡到东西的人往往还没注册，所以我们允许游客直接浏览——否则他第一步就走了。」

2. **切到学生窗口，发布一条**
   - 发布 → 选「招领」→ 标题「灰色保温杯」→ 分类「其他」
   - 描述写「杯底有划痕，在第八教学楼 201 捡到」
   - 地点填「第八教学楼 201」
   - 贵重等级「普通」→ 存放点选「图书馆一楼服务台」
   - 提交 → **状态显示"待存放"**

   > **话术**：「注意这里，他不会直接变成"已存放"——必须由志愿者确认实物收到了，否则失主跑过去发现没有，就再也不信这个平台了。」

---

## 主线二：智能匹配（90 秒）

**讲什么**：这是"智能"两个字唯一站得住的地方——**可解释**。

1. 切到**志愿者**窗口，确认入库
   - 广场里找到刚发的「灰色保温杯」→ 详情 → 「**确认已入库**」
   - 状态变「已存放」，广场上其他人此时也能看到「可认领」

2. **匹配立刻发生**
   - 现在用学生窗口发一条**失物**：「丢了灰色保温杯」分类「其他」地点「第八教学楼 201」
   - 发完点开详情 → **看到"可能相关"列表，有分数和原因**

   > **话术**：「分数是 5 个维度加出来的：分类 25、地点 20、时间 20、关键词 25、保管等级 10。
   > 而且每条都给出原因——**不是黑盒给个百分比**，用户能判断值不值得点进去。」

3. **指向消息中心**
   - 失主会收到「发现一条高相似度信息」
   - 加分项：「70 分以上才通知，而且同一对只通知一次——不然用户编辑一次就收一条。」

---

## 主线三：认领与归还（120 秒）

**讲什么**：失物招领最难的不是发帖，是**确认东西真的还给了对的人**。

1. **学生 A 申请认领**
   - 用第三个学生账号（或管理员冒充失主）点「申请认领」
   - 填说明：「杯底划痕是我的，上周五落在 201」
   - 提交 → 物品状态变「认领中」

   > **话术**：「申请说明我强制要求至少 10 个字——只说"我的"这种，发布者没法判断。」

2. **发布者表态**
   - 切到发布者窗口（志愿者/学生）
   - 详情页看到申请列表 → 点「同意」

   > **话术**：「注意这里是**双签**：发布者只能"同意"，最终发放要授权角色点。
   > 因为发布者可能是学生，他没有核对证件的经验；而志愿者天天在服务台，知道该看什么。」

3. **志愿者终审**
   - 切志愿者窗口 → 点「最终通过」
   - 状态变「待领取」
   - **此时其他待处理申请自动被拒**，申请人收到「请按地址领取」

   > **话术**：「一条物品只能给一个人，所以通过一条的同时，其余申请自动拒绝并通知——不能让五个人都以为能领。」

4. **归还**
   - 志愿者在详情页点「确认已归还」→ 二次确认 → 状态变「已归还」，记录归还时间

   > **话术**：「归还时间会存下来，90 天后自动归档，1 年后连图片一起清除——这是数据保留策略，避免数据库无限增长。」

## 收尾（30 秒）：管理员后台 + 下一步

1. 切**管理员**窗口 → 后台
   - 概览：数字会随刚才的操作变化（初始是 用户 3 / 物品 4 / 待审 1 / 已归还 0，演示完会变成 物品 6 / 已归还 1）
   - 用户页签：能设志愿者、能停用
   - 存放点页签：能新增、能停用

   > **话术**：「所有管理操作都写审计日志——谁在什么时候停了谁的号，都能查。」

2. **讲下一步（诚实讲）**

   > 「现在缺的是公网访问和端到端测试。数据库和接口都有自动化测试（**单元 41 项 + 集成 177 项**），
   > 但真实浏览器里的完整流程还要再过一遍。」

## 可能被问到的问题（准备好答案）

| 问题 | 回答要点 |
|---|---|
| 智能匹配用什么算法？ | 规则打分，5 维加权，不是机器学习。**理由**：数据量小、规则可解释、老师/用户能追问为什么匹配 |
| 为什么不用微信小程序？ | 计划书明确不做。且小程序要审核，来不及；Web 链接能直接发群里 |
| 数据安全怎么保证？ | 密码 scrypt 加盐、会话 HttpOnly Cookie、CSRF 双提交、联系方式认领通过后才可见、演示数据全是假的 |
| 用户量大了怎么办？ | 现在 SQLite 单文件够 500 人/2000 物品；再大换 PostgreSQL，数据层已隔离在 `src/services` |
| 谁维护？ | 志愿者是管理员授权的，存放点是管理员维护的，保卫处暂时挂在一个存放点下 |

## 演示失败预案

| 情况 | 应对 |
|---|---|
| 网络断了 | 放提前截好的图，口头讲流程 |
| 服务起不来 | `npm run db:migrate && npm run db:seed` 重置，30 秒内恢复 |
| 匹配没出现 | 检查招领是否已「确认入库」——**未入库不参与匹配**，这是设计不是 bug |
| 登录不了 | 演示账号密码 `demo1234`；如果被停用过，用管理员重新启用 |
| 时间不够 | **砍掉主线三的第 4 步（归还）**，前三步已能说明完整逻辑 |
